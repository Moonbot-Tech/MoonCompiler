# x86-64 hot-code alignment gate

`run_code_alignment_gate.py` proves the current `-OoCODEALIGN` contract on
x86-64:

- `-O3` aligns procedure entries, natural loop headers and explicit Pascal
  labels to 32 bytes;
- `-O2 -OoCODEALIGN` proves that the switch remains independently usable;
- `-O2`, `-OoNOCODEALIGN` and size optimization preserve the old layout;
- an explicit wider `{$CODEALIGN ...=64}` contract is not narrowed;
- all variants execute the same semantic digest;
- the focused executable stays inside a coarse test-specific code-size guard.

Procedure alignment covers hot routines called by an outer loop, event loop or
network callback.  Natural loop alignment covers compiler-lowered
`for`/`while`/`repeat`; explicit labels cover hand-written `goto` loops.  The
compiler deliberately does not align every internal branch target: without
profile data it cannot distinguish a hot destination from cold error and exit
paths, so doing so would only trade instruction-cache space for speculation.

Referenced explicit Pascal labels are different: the current policy aligns
every one of them.  Therefore the focused 10% guard is not a global size bound;
a label-heavy state machine may accumulate padding roughly in proportion to
its referenced labels.  This is an accepted release trade-off, not a hidden
invariant.  A future bounded/PGO policy needs a real buyer and runtime A/B.

Pulse remains the performance and aggregate code-size oracle.  This gate is a
structural contract and does not treat one favourable benchmark address as a
compiler invariant.

# Placement gate (rules R4, R2, R3, R1)

`run_branch_pad_gate.py` proves the code placement draft of the internal x86-64
assembler (off by default; the gate switches it on with `MOONCOMPILER_PLACEMENT=1`,
and it acts with `CODEALIGN`): no `jmp`/`jcc`/`call`/`ret` or fused
ALU+`jcc` pair crosses or ends on a 32-byte boundary (R4). The checker reports
one-line short-loop (R2) and end-of-line long-loop (R3) targets as diagnostics;
the asserted loop rules are R2E, R2X, R3H, R3L and RT, and procedure entries
must start on a 64-byte line (R1). The fixture
`branch_pad_relax.dpr` is generated by `gen_branch_pad_relax.py`: 504 loops
whose body sizes sweep the short-jump limit, half of them straight-line loops
with calls whose back-edge is short from the first assembler pass on, so a
pad inside the body forces the near encoding.  The gate requires that the
`-O3` build compiles, that the assembler reports `jumps forced near` > 0 and
at most 32 of the assembler's 64 relaxation passes (`-vd`; measured 6-8 on
Win64 and 12-15 on Linux), that `-O2`, `-O3` and
`-O3 -OoNOCODEALIGN` print the same digest, that
`qualification/performance/tools/check_placement_rules.py` finds no violation
of any rule in the placed executable, and that the executable grows by at
most 10% (measured +3.2% on this loop-dense fixture).  The R4 pad bytes must
be realized as DS prefixes on the instructions in front of the branch, not
as executed nops: the gate reads `pad bytes as prefixes N, as nops M (dead
D)` from `-vd` and fails when no prefix was placed or when the executed nop
bytes exceed a quarter of the executed padding (measured 644 prefix bytes
against 188 nop bytes on this fixture, whose call-heavy loop bodies leave
little room in front of each call).

The asserted R2E rule exempts a 64-byte loop from the one-line demand: its
back-edge would end exactly on a forbidden R4 boundary.  Such a loop still
has to use a valid long-loop head (R3H).  R3L rejects an extra fetch line
only when moving the emitted bytes to an allowed head proves a smaller
footprint while preserving R4, RT and short-branch reach.  Its length-only
lower bound remains visible as a diagnostic when that proof is absent.

```powershell
python qualification/optimizer-core/placement/run_branch_pad_gate.py `
  --compiler <ppcx64.exe> --rtl <units/x86_64-win64/rtl>
```

Background and measurements: `doc-int/RTL_PROFILE_STAND_20260914.md`.

# Accepting a placement change

A change to the placement rules is accepted only when it is shown to be
better, not merely different.  The evidence is produced by the stand chains
(`scripts/Stand-F-Chain.ps1` on Win64, `scripts/stand-chain.sh` on Linux),
one run per machine, and all of it has to be green:

1. `qualification/build-driver/config_contract_gate.py` on the variant's
   configuration (the variant assembles internally with the audited options);
2. `qualification/performance/tools/placement_fixture.dpr` built by the
   variant runs correctly and `check_placement_rules.py --assert` finds no
   violation of the rules the variant claims (the fixture carries the loop
   shapes that lost with the first rules: a six-instruction loop, a loop
   just over one line with a call, a big loop with many taken branches, a
   small hot callee called from a tight loop, hand-written assembler with an
   aligned constant, sixteen set tests whose jump target stands between the
   compare and the jump, and the two loops of `CompareText`, where the pads
   used to wipe each other's prefixes until the change limit froze a target
   on byte 62 of its line); the checker also reports the corrected targets R2E,
   R3Z, RT and R1E measured on the loop maps in
   `doc-int/experiments/tiny-loop-map/`; the same check on a product
   toolchain, for CI, is `run_placement_fixture_gate.py` in this directory;
3. the hand-laid parts keep their layout: `qualification/memory-manager/
   mm_layout_gate.py` (the memory manager's hot paths) and
   `qualification/build-driver/rtl_asm_layout_gate.py` (the RTL's
   hand-written block and string routines);
4. in the whole Pulse program of the variant - the program, the RTL units it
   links, compiled and hand-written code alike - no branch crosses or ends on
   a 32-byte boundary and no jump target of a loop lies in the last 12 bytes
   of a line where the block in front could have carried the pad (`compiled
   code rule 4 gate` of the chains, `--assert R4,RT` on Win64 and `R4,RT=2` on
   Linux, where one code shape - `TStringHelper.Split` for `UnicodeString` and
   `WideString` - keeps a target on byte 59 because its pad reached the
   assembler's change limit in that state (`doc/BACKLOG.md`).  Both exact
   procedure identities are required with `--expect-violation`; disappearance
   of one cannot be replaced by an unrelated violation, and a third violation
   also fails.  The list of hand-written routines nobody laid out,
   `unlaid_asm_routines.txt`, is empty);
5. a placement-controlled case-isolated medium Pulse: the baseline family and
   the variant family, four placements each (`-dPULSE_FILLER_1..3`), 190
   cases;
6. `qualification/performance/tools/stand_ab_gate.py` on that result: the
   run was quiet (baseline placement spread median at most 1.05, otherwise
   the run is repeated, not judged), the geomean of variant/baseline is not
   above 1.005, every case the change was made for (`-ExpectFaster`) is at
   most 0.97, and no other case is slower beyond the placement band unless
   it is named in `-AllowSlower` with the reason in the commit message;
   a row is `program/case` (the same case name lives in several Pulse
   programs, and keyed by the name alone one row replaced another), so
   `-ExpectFaster`/`-AllowSlower` take `program/case`, a bare case name only
   while one program of the result has it; `scripts/Pulse-Family.ps1` runs
   the same comparison over every Pulse program (`pulse.py programs --all`,
   `repairs` included), tells the gate which programs it asked for and
   returns the verdict as its exit code;
7. RTL-test and Light on the variant.

The four-placement families are what makes "beyond placement" meaningful:
a difference that lies inside the spread the same code shows at four
positions is not attributed to the change.  `filler_summary.py` prints the
full table behind the verdicts.
