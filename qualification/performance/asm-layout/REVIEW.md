# Проверка ручной ASM-раскладки, 28.09.2026

Исходный пакет отклонён. Все изменения RTL, Generics.Hashes, Math,
Threadvar, syscall и MoonORMot из этого пакета возвращены к предшествующему
состоянию. MM оставлен прежним. Новых раскладок, доказанно проходящих
заданные ограничения, не найдено; массовое снятие выравнивания также отклонено.
Это сохранение исходного поведения, а не доказательство оптимальности прежней раскладки.

Границы: сравнивались предлагаемые изменения с состоянием MoonCompiler
`f0d935782` и MoonORMot `cd81f48b`. Исходные коммиты пакета:
`47dcf26bd`, `eadd28f1b`, `4220e8d62`; MoonORMot `6edfa271`.
После исправления product ASM и MoonORMot version=9 совпадают с исходными
байтами файлов. Позднейшие изменения main этим возвратом не заменяются.

## Доказанные ошибки приёмки

1. `decide.py` исключал положение p0 из основного результата.
2. `famsumm.py` объединял процессы, срезал медленный хвост и усреднял
   положения и входные фазы. `chooseN.py` затем усреднял серии.
3. Широкий A/A занулял измеренную потерю, вместо запрета приёмки.
   Неполное покрытие CPU/серий не блокировалось; порог выигрыша был 5%.
4. Отсутствие подходящего варианта автоматически выбирало x0. Снятие старой
   раскладки является изменением и должно сравниваться с прежним продуктом.
5. Старые inproc-процессы могли завершаться успешно с ORACLE_OK 336/338.
   Пропавшие object-файлы в `lv/verify.py` тоже не увеличивали счётчик ошибок.
6. Проверка загрузки SMT-соседа на Windows не проверяла заявленный peak.
   Linux считывал Cycles без проверки RunningTime/EnabledTime.
7. Raptor Lake E не был отдельной целью. Generic hardware event без выбора
   cpu_atom на этой машине открывался, но имел нулевой RunningTime.

Семантическое различие двух исторических release-оракулов не объявляется
ошибкой действующего продукта. В новом forensic fixture эти исторические
варианты исключены; все зарегистрированные варианты обязаны пройти oracle.

## Свежая проверка

Первый проход: 64 положения 0..4032 с шагом 64, вызывающий на фазах 0/32,
обе входные фазы невыровненных вариантов, все исходные input cases,
три раунда по 100 мкс, два независимых процесса. Шесть Linux-машин:
Zen 2/4/5, Haswell, Cascade Lake, Raptor Lake P. Получено 399360
по-процессных сравнений. Этот короткий проход использовался для отбраковки;
шумные клетки не использовались как доказательство выигрыша.
Полный короткий Windows-проход отвергнут контролем загрузки соседа.

Для единственного ещё не опровергнутого варианта h (`varset contains` Win64)
выполнено подтверждение: семь раундов по 1 мс после одинакового 1 мс прогрева,
по два принятых процесса, все 64 положения × две фазы вызывающего.
Включены Zen 3 / Ryzen 5800X Windows и Raptor Lake E: всего восемь типов ядер.
E-ядро, c0 / p960 / d32: +147.74% и +148.11% времени, A/A максимум 0.07%.
128 клеток дали воспроизводимый провал сверх 5% при чистом A/A.
Вариант h отклонён. Размер set=32 недостаточен для его положительной приёмки
(он меняет и короткий вход <16), но этого отрицательного примера уже достаточно.

Новые выходы не объединяют фазы, положения, случаи или процессы.
Геометрия/oracle fail closed; каждая копия повторно проверяется после
релокации. Нулевой/неработавший PMU не даёт число. Выбор cpu_atom сделан
необязательным аргументом `PulseInitializeCoreCounter`; прежние вызовы с
одним аргументом сохраняют kernel default. Перемещён timestamp после pinning,
чтобы сам старт диагностики не создавал ложную миграцию CPU.
Изменённые perf permissions и boost controls восстановлены после каждого
серверного прохода. Чужие процессы и данные сохранены.

Финальная упаковка исправляет slotbase/warmup metadata, записывает PMU type
и отделяет shuffle state от генератора данных. Порядок теперь задаётся
сохраняемым seed процесса. Повтор на E-ядре с seed=1/2 сохранил провал:
во всех 128 чистых клетках медианный рост времени около 147%.
Embedded ASM blocks и registration при упаковке остались без изменений.

## Что можно считать готовым

Восстановленные System/SysUtils/Math Win64 пересобраны штатными RTL make
command lines. Все 27 проверяемых routine objects и section alignment
побайтно совпали с ref лаборатории; `asm_block_routines_semantic.dpr`
с этими units дал `ASM_BLOCK_ROUTINES_OK`. Отсутствующий object теперь
возвращает ошибку; выполнен отрицательный контроль на пустом каталоге.

Упакованный frozen probe собран на Windows: GEOMETRY_OK 299/299,
ORACLE_OK 299/299. Linux fixture собран и проверен на всех серверных ядрах
в подтверждающем проходе: 296/296. Эти проверки относятся к fixture и
возвращённым исходникам; новая полная release qualification не выполнялась.

Строгий judge прошёл 47 тестов приёмки и отрицательных контролей.
Проверка реального manifest на восьми CPU заново разобрала 2048 сравнений,
побайтно подтвердила raw SHA256, сверила CPU brand/affinity, полную матрицу,
oracle/geometry и статусы контроллера; итог KEEP_OLD / REJECT, 126 hard cells.
Уточнение 29.09: REJECT теперь требует не только узкого A/A, но и разброса
раундов <=2% у ref/aa/candidate во всех повторениях клетки. Две шумные клетки
перестали считаться доказанными потерями; решение по пакету не изменилось.
Подробности: `JUDGE.md`, `h-confirm-manifest.json`, `h-confirm-judgement.json`.

В main можно передавать исправления стенда, строгий judge и документацию.
Исходный performance-пакет передавать нельзя. Версия MoonORMot не повышается.
Восьмиядерное подтверждение h, остальные raw, таблицы, логи rebuild и
отрицательные контроли сохранены в лаборатории. Результаты полного текущего
main отдельно не объявляются результатами этого frozen packet.

64-byte entry alignment управляет остатком адреса внутри линии; оно не
управляет соседями, полным адресом вызова или всеми состояниями процессора.
Этот стенд опровергает универсальные заявления, но конечный прогретый fixture
не гарантирует скорость в произвольной программе. Для будущего принятого
варианта нужны полная объявленная матрица, устойчивый контроль, все важные
входные пути и проверка в потребителе. Если улучшение не доказано — старый layout.
